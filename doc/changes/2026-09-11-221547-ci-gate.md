# 2026-09-11 22:15 加 GitHub Actions 门禁（Node 22 + 24 双矩阵）

## 背景/目的

测试已经沉淀在 `test/` 里，但只有"本地记得跑"才有效。加一条 CI，让每个 PR 与每次 master 推送
都自动跑一遍，改坏了当场变红。

**这条门禁的第一次实跑就抓到了真问题**：workflow 在 Node 22 上跑出一大片
`test did not finish before its parent and was cancelled`，而本地 Node 24 全绿 ——
`node:test` 的父子测试行为在版本间有差异。已在上一个变更里把测试改成扁平顶层写法修掉
（见 `doc/changes/2026-09-11-221313-test-node22-compat.md`），并且把 CI 的 Node 版本
做成 **22 + 24 双矩阵**，让这类版本差异以后也在门禁覆盖范围内。

**能测到哪一层要先说清楚**：微信开发者工具没有 Linux 版，而且自动化还要求工具开着服务端口
并扫码登录，所以 **CI 里跑不了小程序模拟器，做不了真正的界面级 E2E**。CI 覆盖的是纯逻辑层：
排班算法、日历渲染数据、节假日数据、结构完整性、代码卫生。界面层（渲染、换行、点击手感）
仍需人工在开发者工具或真机上过一遍 —— 这条边界写进了 workflow 的注释，
免得后来人误以为"CI 绿了 = 界面没问题"。

## 改动清单

- 新增 `.github/workflows/ci.yml`
  - job `test`，`runs-on: ubuntu-latest`，`strategy.matrix.node: ['22', '24']`，`fail-fast: false`
    （两个版本都要看到结果，不要一个失败就取消另一个）
  - 触发：`pull_request`（base 为 master）、`push`（master）、`workflow_dispatch`（手动）
  - 步骤：
    1. `actions/checkout@v4`
    2. `actions/setup-node@v4`，Node 版本取自矩阵
    3. `node --test test/*.test.js` —— 106 项单元与门禁测试
    4. 全部业务 js 语法检查（`node --check`，覆盖 `app.js` / `pages` / `utils` / `components`，
       含测试没有加载到的设置类页面）
    5. 全部 json 可解析
    6. 打印包体积参考（业务代码与 `pages`/`utils`/`components`/`libs` 各自大小）
- **不引入任何第三方依赖**，CI 里没有 `npm install` 步骤：测试用的是 Node 内置 `node:test`，
  跑得快、也没有供应链面

## 验证方式

- 本地预跑 workflow 里的三个 shell 步骤：106 项测试通过、语法检查 `fail=0`、JSON 检查 `fail=0`
- YAML 用解析器校验通过，job / matrix / 步骤结构核对无误
- **本 PR 自己的 CI 运行就是这条 workflow（含双矩阵）的第一次实跑**，结果见 PR 页面的 checks；
  两个矩阵腿都绿了才合并
- 体积参考：`pages` 400K、`utils` 12K、`components` 16K、`libs` 404K

## 待确认项

- **合并本 PR、确认双矩阵都绿之后**，再把检查设为 `master` 分支保护的必需项。顺序不能反：
  `master` 的保护是 `enforce_admins=true`，先把一个还没验证过的检查设成必需，
  一旦 workflow 本身有问题，连管理员都合并不了任何东西。
  注意矩阵会让检查名变成 `test (node 22)` 与 `test (node 24)` 两个 context，两个都要设为必需
- 只跑 22 与 24 两个版本。测试用的都是稳定的内置能力；如果日后用到更新的语法再扩矩阵
- 是否需要 `concurrency` 取消同分支上被顶掉的旧运行（目前提交频率低，先不加）

## 回滚方式

- revert 本提交即删除 workflow
- 若已设为必需检查，还要把这两个 context 从分支保护里移除，否则 master 谁都合并不了
