# 2026-09-11 21:55 加 GitHub Actions 门禁（PR 与 master 推送都要跑测试）

## 背景/目的

上一个变更把校验沉淀成了 `test/` 里的测试，但只有"本地记得跑"才有效。
加一条 CI，让每个 PR 与每次 master 推送都自动跑一遍，改坏了当场变红。

**能测到哪一层要先说清楚**：微信开发者工具没有 Linux 版，而且自动化需要工具开着服务端口并扫码登录，
所以 **CI 里跑不了小程序模拟器，做不了真正的界面级 E2E**。CI 覆盖的是纯逻辑层：
排班算法、日历渲染数据、节假日数据、结构完整性、代码卫生。
界面层（渲染、换行、点击手感）仍需人工在开发者工具或真机上过一遍 —— 这条边界写进了 workflow 的注释里，
免得后来人误以为"CI 绿了 = 界面没问题"。

## 改动清单

- 新增 `.github/workflows/ci.yml`，job 名 `test`，`runs-on: ubuntu-latest`，触发：
  `pull_request`（base 为 master）、`push`（master）、`workflow_dispatch`（手动）
- 步骤：
  1. `actions/checkout@v4`
  2. `actions/setup-node@v4`，Node **22**
  3. `node --test test/*.test.js` —— 132 项单元与门禁测试
  4. 全部业务 js 语法检查（`node --check`，覆盖 `app.js` / `pages` / `utils` / `components`，
     包含测试没有加载到的页面，例如设置类页面）
  5. 全部 json 可解析
  6. 打印包体积参考（业务代码与 `pages`/`utils`/`components`/`libs` 各自大小）
- **不引入任何第三方依赖**，也不需要 `npm install`：测试用的是 Node 内置 `node:test`，
  所以 CI 里没有安装步骤，跑得快、也没有供应链面

## 验证方式

- 本地预跑 workflow 里的三个 shell 步骤：`node --test test/*.test.js` 132 项通过；
  语法检查 `fail=0`；JSON 检查 `fail=0`
- YAML 用解析器校验通过，job/步骤结构核对无误
- **本 PR 自己的 CI 运行就是这条 workflow 的第一次实跑**，结果见 PR 页面的 checks
- 体积参考：业务代码约 400K（pages）+ 12K（utils）+ 16K（components），`libs` 第三方 SDK 404K

## 待确认项

- 合并本 PR、确认 CI 绿之后，再把 `test` 设为 `master` 分支保护的**必需检查**。
  顺序不能反：`master` 的保护是 `enforce_admins=true`，如果先把一个还没验证过的检查设成必需，
  一旦 workflow 本身有问题，连管理员都合并不了任何东西
- 只跑 Node 22 一个版本。测试用的都是稳定的内置能力，没有多版本矩阵的必要；
  如果日后用到较新的语法，再考虑加一个 20 的矩阵项
- 是否需要给 CI 加 `concurrency` 取消同一分支上被顶掉的旧运行（目前提交频率低，先不加）

## 回滚方式

- revert 本提交即删除 workflow；若已经设成必需检查，还要一并把该检查从分支保护里移除：
  `gh api -X PUT repos/makewheels/shiftcheck-wechat-mini-program/branches/master/protection`（重发不含该 context 的配置）
