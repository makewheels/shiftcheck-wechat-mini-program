# 2026-09-12 00:16 把发版流程写进文档：每个版本都要打 tag + 建 GitHub Release

## 背景/目的

发 2.4.0 时暴露了两个流程问题：

1. **这个仓库从来没有建过 GitHub Release**。`gh release list` 是空的，只有一个孤零零的
   `v2.3.3` tag。tag 只是一个指针，没有给人看的说明、不会被标成 Latest、也挂不了附件 ——
   对使用者（包括几个月后的自己）来说等于没有版本说明
2. **顺序做反了**：先打了 tag，之后又合进 6 个修复，结果 README 的 2.4.0 更新日志比 tag
   少了 7 条，只能回头补一个 PR（`2026-09-12-000740-release-notes-240.md`），
   还强制移动了一次 tag

把正确顺序写进文档，下次照着走就不会再返工。

## 改动清单

- `doc/发布前检查单.md`
  - 新增 **第 8 节「发版收尾（代码侧，别漏）」**：六步顺序
    （README 更新日志写全 → 改 `app.js` 的 `appVersion` → CI 绿并合并 → 打 annotated tag →
    建 GitHub Release → 上传微信），含具体命令、tag 打在哪个提交上的判断标准
    （还没对外发版可以 `git tag -f` 移动，已经发出去了就升补丁号不要移）、
    Release 说明写哪四段、以及 `gh` 偶发 `graphql EOF` 要重试 / 长文本用 `--notes-file` 更稳
  - 原第 8 节「真机自测清单」顺延为第 9 节
  - 自测清单补 3 条本次修复对应的验证项：「自定义规则提醒」页能打开、
    深链进入后「返回主页」能回首页、搜一搜只应搜到首页与倒班查询页
  - 末尾写明「顺序反了的代价」，用 2.4.0 这次的实际情况做例子
- `doc/README.md`：新增「发版」小节，指向上面第 8 节，并说明版本号一致性
  由 `test/hygiene.test.js` 守着（`app.js` 的 `appVersion` 必须等于 README 最新版本号）
