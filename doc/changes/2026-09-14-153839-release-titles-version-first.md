# 2026-09-14 15:38 Release 标题统一成版本号开头（13 个）

## 背景 / 目的

用户指出 releases 列表页上每个标题都是「查班神器 X.Y.Z：…」，产品名重复了一遍：
仓库名里已经有产品名，标题里再写是噪音；而且列表页扫过去时**版本号左对齐才好比较**。
要求改成版本号开头。

因为仓库约定 Release 标题 = `doc/releases/<version>.md` 的一级标题（正文用
`--notes-file` 从文件同步），所以**只改 Release 标题会让两边漂** —— 必须文件和 Release 一起改。

## 改动清单

- `doc/releases/` 下 13 份发布说明的一级标题：`# 查班神器 X.Y.Z：…` → `# X.Y.Z：…`
  （2.0.0 / 2.0.1 / 2.1.0 / 2.2.0 / 2.2.1 / 2.2.2 / 2.2.3 / 2.3.0 / 2.3.1 / 2.3.2 / 2.3.3 / 2.3.4 / 2.4.0）
- `doc/releases/README.md` 新增「标题约定」一节：标题以版本号开头、不带产品名前缀；
  改标题要文件与 Release 一起改（附命令），只改一边就漂
- 合并后对 13 个 Release 执行
  `gh release edit vX.Y.Z --title "<新标题>" --notes-file doc/releases/X.Y.Z.md`，
  标题与正文一次对齐

**不改任何运行时代码、不改测试逻辑、不改版本号。**

## 验证方式

1. 改写脚本自带校验：改完逐份检查 H1 匹配 `^# \d+\.\d+\.\d+：`，13/13 通过
2. **全量测试**：`node --test test/*.test.js` → 139/139 全绿
   （门禁只查"文件存在、非空壳、链接指向 tag"，标题格式不在门禁内；本次靠脚本校验 + 人工核对）
3. 合并后用 `gh release edit` 同步后，回读 API 确认 13 个 Release 的 `name` 均以版本号开头、
   正文首行与标题一致
4. **没验的**：releases 列表页的视觉效果（要人眼看；版本号左对齐是这次改动的目的，改完应自然成立）

## 待确认项

- 标题里**没加 `v` 前缀**（`2.4.0：…` 而不是 `v2.4.0：…`），与 `doc/releases/2.4.0.md` 的文件名、
  `app.js` 的 `appVersion` 保持一致；tag 仍带 `v`（`v2.4.0`），这是 git tag 的惯例。
  若想要标题也带 `v`，说一声，一条命令的事
- 历史 12 份的标题是**只去前缀、其余一字未动**，没有趁机改写措辞

## 回滚方式

- `git revert` 本提交恢复文件 H1；Release 侧用同样的 `gh release edit` 把标题改回
  （旧标题在 git 历史与本记录里都有留档）
