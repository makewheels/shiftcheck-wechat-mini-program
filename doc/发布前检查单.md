## 8. 发版收尾（代码侧，别漏）

按这个顺序做，tag、更新日志、Release 才天然对齐：

1. **先写这一版的发布说明 `doc/releases/X.Y.Z.md`**（完整版：新功能 / 修复带影响 / 隐私与清理 /
   已知边界哪些没验证过）。README 不写更新日志（2026-09-14 起只留指针表格），
   这份发布说明就是唯一的对外口径，写法见 `doc/releases/README.md`
2. 改 `app.js` 的 `globalData.appVersion`（**与上一步同一次改动**）
   （`test/hygiene.test.js` 守着：appVersion 必须等于 `doc/releases/` 里最新的版本号、
   `doc/releases/<version>.md` 必须存在且不是空壳、发布说明里的链接必须指向 tag 而不是 master。
   **还没到发版就两个都不要先动**，门禁会咬）
3. 等 CI 绿、合并到 master
4. **打 annotated tag**：`git tag -a vX.Y.Z -m "..."` → `git push origin vX.Y.Z`
   - tag 要打在"这一版最后一个提交"上。如果之后又合了修复：还没对外发版就把 tag 移过去
     （`git tag -f` + `git push -f origin vX.Y.Z`），已经发出去了就升一个补丁号，不要移
5. **建 GitHub Release，正文从仓库文件同步过去**：
   `gh release create vX.Y.Z --title "<发布说明里的一级标题>" --notes-file doc/releases/X.Y.Z.md`
   （已经建过的用 `gh release edit` 同样的参数）
   - **不要在 GitHub 网页上直接写或改 Release 正文** —— 那样仓库里那份就过期了，两边会漂。
     **仓库文件是唯一事实源，Release 只是它的投影**
   - **每个版本都要建一个 Release**。tag 只是一个指针；Release 才有给人看的说明、
     会被标成 Latest、能挂附件。这个仓库在 2.4.0 之前只有 tag（v2.3.3）、从来没有 Release
   - **发布说明里的链接一律指向 tag**（`/blob/vX.Y.Z/...`），不要指向 `master`：
     Release 是版本快照而 master 会一直往前走，指向 master 的链接将来要么 404，
     要么点开看到的是**另一个版本**的内容，跟这条 Release 描述的东西对不上
   - 网络偶发 `Post "https://api.github.com/graphql": EOF` 时重试即可；
     用 `--notes-file` 比 `--notes "..."` 稳（长文本走命令行容易被截断或转义出错）
6. 上传微信小程序（上一节）

**顺序反了的代价**：2.4.0 就是先打了 tag、之后又合了 6 个修复，结果 README 的更新日志
比 tag 少 7 条，只能回头补一个 PR，还强制移动了一次 tag。
